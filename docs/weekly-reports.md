# Shepherd 毕业设计周报记录

> 说明：本记录按 12 份周报整理，覆盖毕业设计主要研发与论文撰写过程。其中第 4 周完成开题，第 9 周完成中期检查；第 13-14 周可作为论文提交、查重修改和答辩准备阶段，不单独列入本周报记录。

## 第 1 周：选题理解与资料调研

**本周工作：**

1. 阅读毕业设计任务书，明确课题目标为设计并实现一个面向间歇连接环境的分布式节点管理与数据转发系统。
2. 初步梳理 Shepherd 项目的整体结构，区分 Kelpie 管理端、Flock 代理端、Stockman 桌面客户端、协议定义、实验脚本和论文文档等模块。
3. 调研 DTN、store-and-forward、gossip、节点拓扑维护、断连重连和 duty-cycling 等相关技术，为后续系统设计建立背景知识。
4. 搭建本地开发环境，确认 Go、Node.js、Vite、Vue 3、Makefile 等构建链路能够正常使用。

**阶段成果：**

- 完成项目背景和技术关键词整理；
- 初步掌握仓库目录结构和主要模块职责；
- 确定论文大纲的基本方向：需求分析、系统设计、关键实现、实验验证和总结展望。

**遇到的问题：**

- 系统涉及控制平面、数据平面、桌面 UI 和实验脚本，模块较多，初期理解成本较高；
- DTN 与 gossip 的概念需要结合项目代码理解，不能只停留在理论层面。

**下周计划：**

- 深入阅读 Kelpie 与 Flock 的核心代码；
- 梳理节点注册、连接维护、路由转发和消息格式；
- 准备开题报告所需的研究背景和技术路线材料。

## 第 2 周：系统架构分析与方案设计

**本周工作：**

1. 阅读 `cmd/kelpie`、`cmd/flock`、`internal/kelpie`、`internal/flock` 和 `protocol` 等核心目录，分析服务端与代理端的启动流程。
2. 梳理 Kelpie 负责集中管理、拓扑维护、命令下发和状态汇总，Flock 负责节点连接、消息处理、本地执行和转发的职责划分。
3. 分析项目中的 parent-child 拓扑关系、supplemental link、up-carry/down-carry、memo 同步等机制。
4. 结合论文要求，整理系统总体架构图、模块划分和关键数据流。

**阶段成果：**

- 完成系统总体架构说明草稿；
- 初步确定论文中的核心创新点：间歇连接下的最终交付、基于 trace replay 的可复现实验、管理端与代理端协同机制；
- 明确后续实现和测试的重点路径：DTN 投递、gossip 传播、节点休眠恢复和故障切换。

**遇到的问题：**

- 代码中同时存在直接转发、携带转发和 gossip 传播，多种路径之间容易混淆；
- 需要在论文中用较清晰的层次解释系统，而不是直接堆叠代码细节。

**下周计划：**

- 进一步验证基础构建和单元测试；
- 设计开题报告中的研究内容、可行性分析和进度安排；
- 准备第 4 周开题所需的材料。

## 第 3 周：核心流程梳理与开题材料准备

**本周工作：**

1. 运行项目已有构建与测试命令，检查 Kelpie、Flock 和 Stockman 的基础构建状态。
2. 梳理协议消息处理链路，包括节点注册、管理端命令下发、代理端转发、ACK 返回和状态更新。
3. 阅读实验脚本，理解 trace replay 如何启动拓扑、模拟节点行为、采集实验结果并生成 summary 文件。
4. 撰写开题报告初稿，包括选题背景、国内外研究现状、研究内容、技术路线、预期成果和进度安排。

**阶段成果：**

- 完成开题报告初稿；
- 完成核心模块阅读笔记；
- 确定后续实验以 star 和 chain 拓扑为主，重点观察拓扑收敛、DTN 交付率和延迟表现。

**遇到的问题：**

- 开题报告需要把工程系统问题转化为毕业设计语言，表述上需要更正式；
- trace replay 的日志较多，后续需要总结出适合论文呈现的实验指标。

**下周计划：**

- 完成开题答辩材料；
- 根据导师意见调整研究目标和论文结构；
- 开始实现或完善 DTN 相关验证路径。

## 第 4 周：开题答辩与研究方案修订

**本周工作：**

1. 完成开题报告和开题答辩 PPT，围绕研究背景、系统目标、技术路线和进度计划进行汇报准备。
2. 参加开题答辩，记录导师对课题范围、实验设计和论文结构提出的修改意见。
3. 根据开题反馈调整毕业设计计划，明确不追求过大范围功能扩展，而是重点保证系统核心链路可实现、可测试、可解释。
4. 继续阅读 DTN、gossip 和拓扑维护相关实现，准备进入功能完善阶段。

**阶段成果：**

- 完成开题答辩；
- 明确论文主线：面向间歇连接场景的节点管理、消息转发和实验验证；
- 修改论文目录，增加系统设计、关键实现和实验评估章节的比重。

**遇到的问题：**

- 开题阶段系统目标容易写得过宽，需要控制毕业设计范围；
- 实验指标需要兼顾可复现性和论文表达，不能只依赖一次运行结果。

**下周计划：**

- 完善 DTN bundle 投递、ACK 与重试机制的理解和测试；
- 补充 trace replay 场景；
- 开始整理论文第二章和第三章内容。

## 第 5 周：DTN 投递机制分析与基础验证

**本周工作：**

1. 深入分析 DTN 数据投递路径，包括 bundle 创建、路由选择、下行发送、ACK 返回、失败重试和 carry 队列。
2. 阅读 `internal/kelpie/process` 和 `internal/flock/process` 中与 DTN、route、dataplane、carry 相关的实现。
3. 构造基础 trace 场景，验证小规模节点下 DTN payload 能否完成最终交付。
4. 开始整理论文中“关键技术实现”章节的 DTN 机制部分。

**阶段成果：**

- 明确 DTN 交付链路中的核心状态转换；
- 初步完成 DTN 基础场景验证；
- 形成论文中 DTN 存储转发机制的小节草稿。

**遇到的问题：**

- DTN 成功交付不仅取决于路由存在，还取决于子链路写入、ACK 返回和节点在线状态；
- 多跳链路下的故障定位较复杂，需要结合 Kelpie 日志、Flock 日志和 trace summary 共同判断。

**下周计划：**

- 分析 gossip 传播和 memo 同步机制；
- 将 DTN 与 gossip 的交互关系整理清楚；
- 补充相关单元测试和回归测试。

## 第 6 周：Gossip 传播与拓扑收敛实验

**本周工作：**

1. 分析 gossip 消息选择邻居、fanout 控制、父节点回传和邻居传播等实现细节。
2. 运行 star 和 chain 拓扑下的基础回归，观察不同拓扑结构对消息传播和拓扑收敛的影响。
3. 整理 trace replay 输出数据，初步确定论文实验中的节点数、拓扑类型、重复次数和评价指标。
4. 检查 Stockman 客户端的功能定位，梳理其在系统演示和状态观察中的作用。

**阶段成果：**

- 完成 gossip 传播机制阅读；
- 初步完成拓扑收敛实验设计；
- 明确论文实验指标包括收敛时间、DTN 交付结果、重试次数和日志观测结果。

**遇到的问题：**

- chain 拓扑比 star 拓扑更容易暴露多跳传播和连接恢复问题；
- 实验数据需要经过统一脚本整理，否则难以直接放入论文。

**下周计划：**

- 继续完善实验脚本和数据生成流程；
- 分析节点休眠、唤醒和 failover 相关逻辑；
- 准备中期检查前的阶段性成果整理。

## 第 7 周：节点休眠、故障切换与回放场景扩展

**本周工作：**

1. 阅读节点 sleep/work duty-cycling 相关逻辑，分析节点休眠对 DTN 投递和 ACK 返回的影响。
2. 梳理 parent 失效后的 failover candidate 选择、连接接管和节点唤醒保护机制。
3. 扩展 trace replay 场景，增加节点休眠、父节点失效、链式拓扑等更接近异常环境的验证路径。
4. 在论文中补充系统可靠性设计，包括断连恢复、延迟投递和最终一致性说明。

**阶段成果：**

- 完成 duty-cycling 与 failover 相关机制分析；
- 增加异常场景回归思路；
- 完成论文系统设计章节的大部分初稿。

**遇到的问题：**

- 节点休眠会导致实验时间变长，需要合理设置 trace 的超时时间；
- failover 与 supplemental link 之间存在交互，后续需要重点检查是否会产生过期路由。

**下周计划：**

- 集中进行中期检查前的系统整理；
- 生成阶段性实验结果；
- 准备中期报告和展示材料。

## 第 8 周：阶段性实验与中期材料准备

1. 按照论文实验设计运行拓扑收敛和 DTN duty-cycling 场景，收集 CSV、SVG 和 summary 结果。
2. 整理目前已实现的功能：Kelpie 管理端、Flock 代理端、DTN 投递、gossip 传播、trace replay 和 Stockman 客户端。
3. 编写中期报告初稿，说明已完成内容、当前进度、存在问题和后续计划。
4. 对论文结构进行一次整体调整，使章节顺序更符合毕业论文写作规范。

**阶段成果：**

- 完成中期检查材料初稿；
- 获得第一批可用于论文的实验图表和数据；
- 明确后续重点从“功能实现”转向“稳定性验证和论文完善”。

**下周计划：**

## 第 9 周：中期检查与问题修正

**本周工作：**

1. 完成中期报告和展示材料，参加中期检查，汇报系统实现进度、实验结果和论文完成情况。
2. 根据中期反馈进一步明确论文需要加强的部分，尤其是实验设计、结果分析和系统可靠性说明。
3. 对 trace replay 场景进行复查，重点关注多跳 chain 拓扑、连续 DTN memo 投递和节点异常恢复。
4. 开始定位高风险回归中暴露的问题，包括路由选择、ACK 时序、写入失败处理和 gossip fanout 边界情况。

**阶段成果：**

- 完成中期检查；
- 梳理出后续必须解决的几个稳定性问题；
- 明确论文定稿前需要补充更有说服力的工程回归结果。

**遇到的问题：**

- 小规模实验通过不代表复杂拓扑稳定，17 节点 chain 场景更容易暴露隐藏问题；
- 连续 DTN memo 投递时，第二条消息可能受到旧路由、ACK 时序或链路状态影响，需要深入分析。

**下周计划：**

- 修复 DTN memo 高风险回归问题；
- 补充单元测试和 trace replay 回归；
- 更新论文实验验证部分。

## 第 10 周：高风险回归修复与测试增强

**本周工作：**

1. 针对 17 节点 `gossip_memo_scale_n16` 回归进行深入排查，分析 DTN delivered 计数、ACK 返回、memo 可见性和节点日志。
2. 完善协议写入路径，增加写超时和错误传播，避免下行链路写入异常被忽略。
3. 调整 DTN memo 的处理时序，使节点先完成 ACK 相关流程，再进行 memo snapshot 发布，降低传播副作用对确认路径的影响。
4. 修复 gossip `fanout=0` 被误解释为泛洪所有非父邻居的问题，补充对应单元测试。
5. 完善 trace listener 的 transient retry 逻辑，降低回放启动阶段的偶发失败。

**阶段成果：**

- 修复 DTN memo 连续投递不稳定问题；
- 补充 gossip fanout、DTN route、carry retry、failover wake 等测试；
- 17 节点 star/chain 回归均达到 2/2 DTN memo 交付。

**遇到的问题：**

- 直接强制使用主树路由会导致长链路下延迟和 failover 压力增大，因此最终采用“首次按正常路由，重试后回退主树路由”的策略；
- 一些失败发生在回放启动阶段，需要区分系统业务问题和测试基础设施问题。

**下周计划：**

- 运行完整单元测试、race 测试和 trace replay；
- 将最终实验结果写入论文；
- 开始论文全文润色和格式统一。
